## Foreword

之前玩AC用过好几个Su7 Ultra Mod，原型车的圈速很快，量产车的外观和功能又更接近真车，但是玩得越多，就越能发现里面的问题。

有的参数只是大概像，有的轮胎只是换了一个名字，TC、ESC、TVC也基本还是AC原生逻辑。真车在珠海已经有了不少完整圈和HUD视频，再拿一个普通四驱车换个外壳，就有点对不上了。

特别是真车的不同参数的配置，实际开的时候在极限工况下，车的表现完全不一样，单纯用AC的mod练车实际效果不明显，真车和模拟器差距有点太大了，除了熟悉赛道，并不能把模拟器的开发或者驾驶经验拿到现实里，所以这次干脆重新做了一个。

这个“重新做”不是从Blender开始画一辆车，3D模型、内饰和声音还是用现有Mod做底子，我主要重做的是物理、轮胎、硬件组合、电控和验证流程。这次也基本没手写什么代码，主要是给Codex找资料、定边界、看实测结果，发现不对就让它继续改。



## AC车辆Mod

一个AC车辆Mod表面上就是`content/cars`下面的一个文件夹，但是里面其实拆得很散。

```text
content/cars/acr_su7_ultra_air
├── *.kn5             车身、内饰、轮毂等3D模型
├── data              动力、轮胎、悬挂、气动、刹车等物理
├── extension         CSP配置和Lua物理脚本
├── sfx               声音bank和GUID
├── skins             车漆和皮肤
└── ui                CM里显示的车名、图片和规格
```

从零开始做当然还要处理3D建模、材质、动画、驾驶员坐姿、方向盘角度和LOD，这部分这次没做。现成车壳能省掉很多时间。

首先车辆ID一变，声音GUID、bank和一些扩展配置都可能跟着失效。其次AC的物理可以放在`data`文件夹，也可以打包在`data.acd`里，两个同时存在时还可能读到旧的ACD，明明改了参数，进游戏一点变化都没有，大概率就是这里的问题了。



## 车辆物理

前面这些只能说明一辆AC的车由什么组成，真的到了专业Mod制作，美术和物理其实是两条并行的线。有些Mod展厅看起来很精细，但开起来和真车没什么关系；也有些项目只发布物理文件，外观和声音反而借用现成车。



### Kunos官方流程

AC自带的SDK里有一份官方`Car Pipeline`，重点是教怎么把一个3D车模正确放进游戏。

专业的美术制作一般先把车按1:1尺寸建好，拆出车身、轮胎、轮毂、刹车盘、方向盘、雨刷和各种可动部件，再按AC规定的名称和层级放好旋转中心。官方流程要求一辆车有高模、3级LOD和一个低模碰撞体。

模型和UV处理完以后导出FBX，再进`ksEditor`配材质、反射、透明、贴图和阴影，最后导出KN5。驾驶舱高低模、轮毂模糊、灯光、仪表、破损和动画都有固定命名。这一步主要解决“看起来像不像”和显示性能优化，并不会自动生成正确的车辆物理。



### Arch的物理流程

AC社区里比较有代表性的是Arch公开的`Girellu Physics Pipeline`。他的方法不是先进游戏试手感，而是先建一张数据底表，把能找到的原厂手册、维修资料、轮胎规格、变速比、实测和照片尺寸放在一起。

他还公开了Car Analyzer、Tire Load Curve、Wheel Rate、Torsion Bar、Damper、Brake和轮胎温度等一套计算表。从这些工具就能看出来，他们不是单独调一个摩擦系数，而是把整车分开处理：

- 车重、轴距、轮距、配重、重心和簧下质量
- 悬挂几何、运动比、轮端刚度、防倾杆、限位和阻尼力
- 轮胎半径、垂向刚度、载荷曲线、滑移、侧偏、温度和磨损
- 动力曲线、传动比、传动损耗、风阻、下压力和刹车

AC的轮胎是经验模型，制作者还是要填参数和LUT。找不到原始数据时，通常是找同年代、同规格、同用途的车或轮胎当代理，再把假设记录下来。

Arch公开的车甚至可以只发物理，安装脚本自动寻找原车作为外观和声音的donor。这和我这次保留原模型、单独重做物理的方向其实比较接近。



### 商业团队的做法

Race Sim Studio这类商业团队的分工会更明确，3D车辆、物理、声音和工具链是不同工种。他们对物理的官方描述是数据驱动，再加真实车手、赛车队和模拟器中心的反馈，轮胎、可驾驶性和平衡也是单独工作项，不是最后试跑一圈再一起调。

另外一个容易被忽略的地方是工具链，他们会固定命名、版本、文档和涂装模板。一辆车后面可能要更新几年，只靠某个人记得“当时这个INI为什么这样写”，基本不可能维护。



### 检验

前面三种做法合在一起，基本就是一个完整的Mod流程：

1. 先定义车型、年份、硬件和轮胎，不把不同版本的数据混起来
2. 把外观和物理都按真实尺寸建好，每个数值记录来源和可信度
3. 先验证质量、几何和静态输出，再分别测加速、刹车、稳态转弯、瞬态转向和轮胎温度
4. 对比真车遥测和车手反馈，一次只改一类问题，不用一个最终圈速遮掉中间全部错误
5. 在不同赛道、胎温、车速和调校下复测，最后再封包，检查LOD、声音和发布版本

现代AC Mod还会用CSP的悬挂扩展和物理Lua，加入运动比、弹簧/阻尼曲线、限位、主动气动或自定义电控。但CSP只是多给了一些工具，只是靠Lua脚本机械降神并不行，前提还是有可靠的数据和测试。

我这次的流程大方向和他们是一样的，差距也很明显：没有原厂CAD、轮胎台架、避震器台架、CFD、ECU标定和完整车辆CAN数据，现在主要靠公开参数、实车视频、AC Replay和实际驾驶感受去反推，所以还原还是有限的。



## 制作流程

### 车型

SU7 Ultra量产车不是只有一个形态，普通双腔空悬、Bilstein赛道绞牙、升降尾翼、固定大尾翼、P ZERO 5、Trofeo RS、PT01，这些搭配不同实际驾驶体验都不是一回事。

以前很容易看到一个圈速很快，就把这辆车的轮胎、悬挂、翼片和电控全当成是一套。实际上有的记录车换了绞牙，有的用了半热熔、光头，有的还有额外气动和安全改装，拿来做数据是没控制变量的，比较麻烦。

所以现在包里分了两辆独立车：

- `acr_su7_ultra_air`，普通量产空悬的等效版
- `acr_su7_ultra_coilover`，赛道绞牙的实验版

车型主要是避震的区别，尾翼和轮胎再独立选。



### 参数

官方页面可以找到车重、轴距、轮胎尺寸、电机功率、制动距离、极速和高速下压力，这些先作为锚点。比如轮胎的前265/35R21、后305/30R21，但是实际上这个指标水分也颇多，不同轮胎的这个尺寸完全不一致。

但官方宣传参数不能直接抄进AC。电机峰值功率不等于全速域轮上持续功率，285kg下压力还得知道对应的车速和前后分配，100-0制动距离也不能反推出整条轮胎曲线。

这里大概拆成了几部分：

- 质量、轴距、轮胎半径这种有公开值的，先按公开值对齐
- 功率曲线用主直道分段加速去对
- 气动用高速下压力和CdA核对，升降尾翼和固定尾翼分开
- 悬挂区分空悬和绞牙，不把弹簧刚度和轮端刚度当成同一个值
- 轮胎的纵向抓地和横向抓地分开标，不用一个总摩擦倍率调圈速

PT01是这里最麻烦的一块。赛轮公开资料只能确认它和SU7 Ultra合作开发，但没有轮胎台架的`Fx/Fy/Mz`曲线，温度、压力、磨损和载荷敏感也都没有。

现在的做法是以原来的半热熔胎做代理，再用真车和AC的同一刹车段、同一弯区去估纵向和横向的差异。即使如次，还是有一部分数据是摸不出来的，只能猜测个大概。



### 电控

原Mod本质上还是一条总扭矩曲线加AWD固定分配，AC原生TC可以控制打滑，但是它不知道SU7 Ultra的三电机到底想干什么。

这次把AC原生TC关掉，改成CSP Lua里的自定义控制：

- TC看四轮滑移，通过总驱动扭矩曲线减扭，0-8档是不同目标滑移
- ESC看目标横摆、实际横摆和车身侧偏，加一个受限的等效横摆力矩
- TVC按后轮当时还有多少驱动力去算左右差动，只改横摆，不凭空增加纵向推力

三个逻辑是分开的，不是选一个更强的档位就把全车马力乘个百分比。Track、ESC、TC、TVC都可以在车辆调校页选，但是这些数值是AC里的等效工程映射，不是小米ECU标定表，小米电控自己也改了几次，而且实际标定细节是不知道的，只能通过实车在极限工况下反向推测这个参数的标定范围大概是什么。

这里也有一个比较大的限制：尝试用CSP对四个轮子独立施加电机扭矩时，原车AWD传动系的电机转速会不稳定。所以现在ESC和TVC还是车身等效横摆执行器，效果方向和限幅都能验证，但不能说已经还原了每一台电机的瞬时扭矩。



### 配置脚本

如果只改一辆车，手工改INI也不是不行。但是这次有两种悬挂、两种尾翼、三种轮胎，光基础组合就有12种，再加阻尼、车高和电控档位，靠手工复制很快就不知道哪个文件改过了。

所以现在是用构建器从底包重新生成：

```powershell
python tools/su7-mod/build_mod.py --suspension air --wing fixed --tyre pt01 --damper-click 5 --height-mm 0 --esc 2 --tc 4 --tvc 0
```

也可以直接双击`Configure_SU7.cmd`用界面选。每次生成会带一份`variant_manifest.json`，记录这辆车到底用了什么悬挂、尾翼、轮胎和电控，还会记录原物理的哈希。

这样后面发现PT01的纵向抓地不对，只需要改一处模板再重新生成，不用去十几个车辆目录里找自己上次改了什么。



### 测试标准

做Mod最容易出现的问题，就是调到某一圈圈速差不多，然后就觉得做完了。

这种调法很容易把线路、驾驶、轮胎和动力的误差全部混在一起。轮胎抓地开高一点，马力再加一点，圈速当然可以对上，但是主直道加速、刹车段和弯中速度可能全是错的。

现在大概分成四层测试：

1. 先做静态检查，看资源、LUT、轮胎、尾翼、电控档位和原文件哈希是否对
2. 用完全相同的初态和输入做固定油门、固定转向和制动测试，一次只改TC、ESC或TVC的一项
3. 再进AC实际跑，看CSP接口单位、方向、执行限制和车辆是不是真的按预期反应
4. 最后才用真车视频、AC Replay和完整圈做分段对比，分开看直道、刹车、弯心和出弯

完整圈的人为输入波动太大，后面又做了一套AC自主控制器。它不用AC内置AI额外加抓地，而是像人一样操作方向、油门和刹车，每圈保存完整遥测。这样才能在同一个热状态下重复跑几组参数，而不是每改一个值都得靠我自己再开几个稳定圈。



## 目前结果

最早的完整验证版是空悬、固定大尾翼、PT01，Track / ESC2 / TC4 / TVC0，自主控制器跑出了1:42.422。这一圈不是为了追求最快，主要是用来证明包可以加载、电控在工作、整圈不会突然出界。

后面又按真车珠海1:38.28的Track / ESC0 / TC1 / TVC2继续调，现在严格可重复的圈速到了1:39.281，这个比惠玮哥的走线更保守，没有压草，赛道也不是用尽的状态。

距离1:38.28还有大概1秒，而且这一秒不能简单用加马力或加抓地填上。现在看更多还是行车线、制动到转向的瞬态和控制器没有把车的能力全部用出来，所以还在继续磨，已经跑了一周了，但是AI搜索速度还是很慢，距离人工记录还是有差距。

## Summary

从这次的经验看，AC做一辆能开的Mod并不难，改一下车重、马力和轮胎就能跑了。难的是知道每个数字从哪里来，修改以后到底改对了什么，还有下次能不能用同样的条件再跑出来。

做到后面已经不太像传统意义的“调Mod”了，更像是一个不完整的车辆工程项目：先找证据，再建模，然后进AC测，不对就回来改。至少现在每一圈快在哪、慢在哪、有没有偷抓地，都能说得清楚了。
