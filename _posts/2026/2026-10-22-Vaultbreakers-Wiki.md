## 静态资源

装好游戏之后，我先把安装目录打开，这一步不写解析。只看文件夹叫什么、文件叫什么、文件有多大。

根目录里 `Vaultbreakers.exe` 是双击就能启动的程序。它旁边有 `UnityPlayer.dll` 和 `UnityCrashHandler64.exe`。文件名里带 Unity，这款游戏是用 Unity 做的。

还有一个很大的 `GameAssembly.dll`。我在旁边找 `Managed` 文件夹，没有。Unity 如果把 C# 脚本按原来的 dll 留下，这个文件夹里会有很多可以用反编译工具打开的文件。这里没有那些 dll。脚本被编译进了 `GameAssembly.dll` 这一个文件。在根目录里翻，找不到掉落表。

资源在 `Vaultbreakers_Data`。

这个目录里有一批名字，换一款 Unity 游戏也还是这些：`globalgamemanagers`、`level0`、`sharedassets0.assets`、`resources.assets`。`Resources` 文件夹里还有 `unity default resources` 和 `unity_builtin_extra`。名字里写着 default、builtin 的，是引擎自己带的图和配置。`resources.assets` 和旁边的 `resources.assets.resS` 加起来有五百多 MB。文件名是 Unity 规定好的，不会写成某一张地图或者某一种物品。它是游戏一启动就要加载的那一包。

`StreamingAssets` 里面有一排 `.bank`。名字是单词：`Music.bank`、`Voices.bank`、`Enemies.bank`，还有 `Wolfswood.bank`、`Dragonvault.bank`。音乐、语音、敌人、地图名都能读出来。这是声音文件。后面做物品图标时用不到。

再往下是 `StreamingAssets/aa`。这里有一个 `settings.json`，用记事本打开就能看。里面写着 Addressables，版本是 `2.9.1`，目录文件叫 `catalog.bin`，平台叫 `StandaloneWindows64`。旁边正好有一个同名文件夹。

Addressables 是 Unity 用来查资源的一份目录。程序里写一个能读懂的名字，比如某张图标。磁盘上的文件可以叫一串编号。游戏运行的时候，按这份目录去找那个文件。

`StandaloneWindows64` 里大约有一万一千个文件，后缀都是 `.bundle`，一共五个多 GB。上面的 `resources.assets` 大约五百多 MB，这边差不多是它的十倍。最大的一个 bundle 有六百多 MB。

这些文件的名字是一长串十六进制数字，里面没有 icon、map、item 这种单词。原来的路径被做成了哈希。哈希算出来的字符串长度固定，从这个字符串看不回原来的单词。站在这个文件夹里，可以确定游戏自己的图、场景和配置几乎都在这里。看不出哪一个文件是图标，哪一个是场景。

`aa` 里、这个大文件夹的旁边，有 `catalog.bin`，大约六 MB，还有一个很小的 `catalog.hash`。catalog 就是目录。后面要读的是这份目录：程序里用的那个可读名字，对应这里的哪一个哈希文件。不能在一万个文件里一个个打开试。

另外两个文件的名字容易让人以为里面就是数据表。`il2cpp_data/Metadata/global-metadata.dat` 是配合 `GameAssembly.dll` 的。它记录游戏里有哪些类、类上有哪些字段。它没有「某一行掉了什么」这种内容。

`ScriptingAssemblies.json` 列的是编译时用过哪些程序集，也就是那些本来会变成 dll 的名字。里面有 `Unity.Addressables`、`Unity.Localization`、`FMODUnity`、`MessagePack`。这和目录对得上。资源用 Addressables 管理。玩家看到的译文走 Unity 的本地化。声音用 FMOD，上面那些 `.bank` 就是它的文件。还有一份数据用 MessagePack 打包，MessagePack 是一种二进制格式，用很少的字节表示字符串和整数。这些 dll 的名字在名单上，磁盘上找不到文件，因为它们和游戏脚本一起编进了 `GameAssembly.dll`。

`BepInEx`、`winhttp.dll`、`loot-wiki` 是后来放进游戏目录的。安装包里原来没有。看游戏自己的文件时先把它们拿开。



## 打开 .bundle

这些 `.bundle` 用解压软件打不开。用记事本看文件开头，能看到一行明文字 `UnityFS`。这是 Unity 自己的打包格式。一个 bundle 里面装着好几个小文件，而且通常压过。

带界面的工具可以拿来对照。AssetRipper 能把某一个包展开，看看眼睛认不认得里面的对象。资料页要反复生成，解析就写在 Node 脚本里。解压用 `lz4js`，写 PNG 用 `pngjs`。类和字段的名字用已经放在旁边的 `il2cpp/dump.cs`。那是 Il2CppDumper 读了 `GameAssembly.dll` 和 metadata 之后写出的文本，样子像一份 C# 类定义。不用每次再从正在运行的游戏里抓。

文件头按大端存放。一个整数如果占好几个字节，大端是把高位的那个字节放在前面。头里面依次是格式版本、Unity 的版本字符串、修订号、整个归档有多大、后面那份块信息压缩之后有多大、解开之后有多大，以及一个叫 flags 的整数。这批文件的格式版本是 8。版本号大于等于 7 时，文件头的长度要补到 16 字节的倍数。

flags 这一个整数里塞了好几件事，看的是不同的二进制位。低 6 位用 `flags & 0x3f` 取出来，表示怎么压缩。这里取出来是 3。2 和 3 都用 lz4 解开一块数据。lz4 是一种压得很快的算法。`0x40` 这一位表示压缩块的列表和文件目录写在一起。`0x80` 这一位如果有，目录会放在文件的末尾。这批文件没有这一位，目录就跟在文件头后面。`0x200` 表示真正的文件数据开始之前，位置要先补到 16 字节的倍数。

目录解开之后，前面 16 字节是用来校验的一段数据，然后才写有多少个压缩块、每一块有多大。再后面是节点。一个节点就是包里的一个小文件：解压之后从第几个字节开始、有多长、自己的标记，以及一个以 0 结尾的路径。路径大多是 `CAB-` 再加一串编号。这个 CAB 文件才是后面要读的资源。贴图的像素经常不在 CAB 里，而在同一个 bundle 的另一个小文件里，路径以 `.resS` 结尾。CAB 里只记下到那个文件的第几个字节、读多长。

小的 bundle 可以把压缩块按顺序全部解开，拼成一整段，再按节点上的位置把 CAB 切出来。场景用的 bundle 有几百 MB。如果只是为了读里面一个对象就把整段拼起来，内存会一下涨上去。这种包只解目录，算出那个小文件落在哪几个压缩块上，只解那一段。解开之后的长度如果和头里写的不一致，这一步就已经错了，后面的字段不要继续猜。



## 资源文件里的字段

切出来的 CAB 还不能当成一张表来看。它是 Unity 的序列化文件。前面是一个头。中间是一棵树，树上写着这个文件里有哪些类型、每个类型有哪些字段、每个字段占几个字节。树的后面才是一条一条对象的数据。

头是试出来的。前几十个字节，同一个位置按大端读一次，再按小端读一次。小端把低位字节放在前面。要找到两个能对上的数。一个落在这种文件常用的版本号范围里。另一个等于这块数据自己的长度。对上之后可以确定：这批文件的头用大端。头里还有一个字节，写明后面的正文用小端。

版本号大于等于 22 时，头里会再写一组数字，用 32 位和 64 位记下前面的说明有多大、整个文件有多大、正文从第几个字节开始。如果还去读旧位置上的那组 32 位数字，正文的起点就会指错。后面每一个字段都会跟着偏。

版本号大于等于 23 时，那棵类型树包在一块带 `mhtt` 这四个字母的数据里。每个节点上的类型名和字段名，有时直接写在文件里，有时只写一个编号，要到 Unity 自带的一张公共字符串表里去查。这个编号是那张表里的字节位置，不是「第几个名字」。编号的最高位如果是 1，表示要去这张公共表里查。

公共表里，`float` 这个单词放在第 159 个字节。这版游戏的类型树写的编号是 161。161 在表里没有单词，读出来就显示成 `#161`。

程序只有在类型名正好是 `float` 或 `double` 的时候，才把这几个字节当成小数。`#161` 仍然占 4 个字节，于是被当成普通整数。地图坐标第一次全是很大的整数，就是这个原因。那 4 个字节本来是一个小数的二进制，被当成整数看了。后来只在读坐标的地方，把这 4 个字节再按小数解释一次。已经是正常小数的数不动。所有 4 字节的数都不能改成小数。同一段代码还要读物品编号这种真正的整数。全部改掉，掉落表会整张错位。

字段名用的是同一套编号。物体的名字读出来叫 `#427`。表示位置的那个组件，指向物体的字段叫 `#374`。`dump.cs` 里这两个字段写的是 `m_Name` 和 `m_GameObject`。公共表里这两个单词的位置，和类型树用的编号差了一点，所以对不上英文。认对象的时候先看 classId。这是 Unity 给内置类型的固定编号。场景里的物体 GameObject 是 1。管位置、旋转和缩放的 Transform 是 4。编号对上之后，按 `dump.cs` 里的字段顺序，和一个字段占多少字节，往下读。名字暂时是 `#427`，值还是能读出来。

字符串在文件里是这样放的：先用一个 32 位整数写后面有几个字节，然后是 UTF-8 的内容，最后把位置补到 4 的倍数。一个对象指向另一个对象时，用的结构叫 PPtr。里面有两个数。fileId 表示在哪个文件。pathId 表示那个文件里的哪一个对象。pathId 是 64 位整数。共享字符串的编号、中文表里每一行的编号也是 64 位。JavaScript 里如果把它们转成普通的 number，超过安全范围的高位会被丢掉，两个不同的对象会变成同一个。这些编号一直用十进制的字符串保存。

类型树上有的字段带一个对齐标记，算出来是 `meta & 0x4000`。这种字段读完以后，要把当前位置补到下一个 4 字节的边界。漏一次，后面的对象就全部偏掉。



## 贴图

贴图的像素经常和它的说明分开存。类型树里会写下长度和起始位置，指向同一个 bundle 里那个 `.resS` 文件的某一段。

这批图只碰到三种格式编号。4 是没有压缩的 RGBA，一个像素四个字节，依次是红、绿、蓝和透明度。10 是 DXT1，12 是 DXT5。DXT 把 4 乘 4 的一小块像素压在一起。别的编号先跳过，不用另一张图去代替。解开之后用 `pngjs` 写成 PNG。

Unity 里，贴图的第一行像素在图片底部。按读到的顺序直接写成 PNG，图是倒的。写文件的时候要把上下对调一次。

左右要不要再翻一次，是后来把 PNG 和游戏窗口里的图放在一起看出来的。这次和上下颠倒不是同一件事。图标需要再左右翻一次。小地图的底图不要跟着翻。网页上一个点的位置，是按拍这张小地图的相机算的。画面右边是世界坐标里 X 变大的方向，上边是 Z 变大的方向。底图如果再左右翻，算出来的点和像素就反了。

脚本如果发现这张 PNG 已经在磁盘上，就不再写一遍。这样同一次翻转不会被做两次。要改某一张图的方向，先把那张 PNG 删掉，再运行脚本。



## 用编号把记录连起来

类型树能读了以后，到 `dump.cs` 里看枚举和配置类的字段是什么顺序，再回到资源文件里找带这些字段的对象。

同一件东西在数据里有三种名字，查找的时候不能拼成一个字符串。

第一种是枚举里的整数。某种掉落表在枚举里是一个数字，资源文件里写的也是这个数字。两张表要连起来，用的是它。

第二种是给程序看的英文名，放在另一个字段上。

第三种是玩家看到的中文。中文不写在这行记录里面。有一个共享字符串的包，里面把一个短名字对到一个 64 位的编号。这个短名字叫 key。语言包里，对象名字以 `_zh` 结尾的，把同一个编号对到简体中文。两张表用编号接上，才有中文。正文里如果出现 `{@表.key}`，再拿 key 去换成对应的句子，并且最多换几层。不限制层数的话，两段文字互相引用会停不下来。换完以后去掉 HTML 标签。编号对不上，或者中文是空的，页面上留原来的英文。

掉落表的每一行长度是固定的。把 `dump.cs` 里每个字段占的字节加起来，就是这一行有多长。这批数据里一行是 `0x50`，也就是 80 个字节。

行里有的格子是权重。用这一行的权重，除以同一组里参加这次抽取的那些权重之和，得到它占多少比例。有的格子里存的是一个放大过的整数，除回去才是百分数。概率那一格是 64 位整数，除以 65536。除完之后，25 就是 25%。页面如果再乘 100，会显示成 2500%。同一行里还可以再有一组权重。那一组表示这一行抽中之后，各个品质各占多少。它和「这一行会不会被抽到」是前后两次计算。

一行也可以不指向一件物品，而指向另一张表的编号。子表如果在页面上用了和父对象一样的中文标题，点进去会看到同一个名字，像是绕回来了。展开的时候用编号，不用页面上的标题。

有的对象自己没有嵌进这些行，但是有一个整数，值等于某张表的编号。这个对象就是来源，比如一只怪物或者一个箱子用了哪张表。页面标题写什么中文，只影响人看到的字。查找用那个整数。

场景里的一个点也这样连。物体有一个名字。文件里写的往往是相对父物体的位置，不是地图上的最终位置。这个相对位置在 Transform 上。要沿着父物体一层层算上去，父物体自己还有父物体就继续。父物体那个引用的 pathId 如果是 0，说明到了最外层。算的时候要把旋转乘进去。旋转在文件里是四个小数。物体的名字再去对枚举，或者对表的编号。场景里的字符串和资源上的英文名经常不一样，多一个前缀，多一个序号，或者干脆是另一个叫法。对不上的物体不放进页面。旁边有一块区域，或者其他物体的坐标看起来差不多，也不拿来填这个空位。

有的刷新记录是一组候选。这一组自己的坐标可以在原点，也就是 0,0,0。真正的位置在它的子物体上。子物体上的权重大于 0，这一局才可能用到它。有的门也是这样。父物体在原点，看得到的模型在子物体上。页面上要标的是子物体算出来的位置。

中文标题还会和另一套 key 碰上。场景里交互时显示的那句中文，和仓库里某件物品的中文，可以很像。它们的 key 不是同一个。查找仍然用表的编号，或者枚举里的那个整数。



## 小地图上的点落在哪

小地图的底图是事先做好的一张图，存在 bundle 里。要把场景里的一个物体画到这张图上，得先知道这张图盖住了世界里哪一块矩形。

第一次用的是场景里负责剔除的组件。剔除用来决定远处的东西还要不要画。它上面有 `_worldSize` 和 `_worldOffset`，看起来像地图的宽高和起点。某一张图上，这块矩形大约是 600 乘 600。

拍出这张小地图的是一台正交相机。正交就是没有近大远小，地图适合用这种相机。代码里它的视野这样算：覆盖尺寸里比较长的那一边，加上 15，再除以 2。15 是写在程序里的一圈边距。能看见的范围是一个正方形，中心在这台相机贴着地面的位置。画面的右边是世界坐标 X 变大，上边是 Z 变大。高度是 Y，画在平面地图上不用它。

两块矩形差不多大，所以第一次看的时候，一个方向还接近，另一个方向越往边上越偏。把整张图平移，只能让一个点对准，别的点会一起挪走。后来点的位置和区域的边线都改用相机这块矩形。

区域的边来自挂在物体上的 Sprite，就是一张 2D 图片。用它的顶点，或者用图片上不透明像素的外圈，乘上这个物体的缩放和旋转，再放进相机那块矩形里。场景里还有别的组件，名字里也有 Area。那是给别的系统用的多边形，不拿来当这张小地图的边界。

底图按贴图的底部原点上下对调过之后，又曾经把图和点一起转 180 度，再转 90 度。一起转的时候，点相对像素的位置没有变，看起来还是偏。最后只留相机规定的方向。拿两个在游戏里已经知道位置的地标去对。两个都落在该落的像素上，这套算法才用。



## 配置包里没有的记录

技能、任务、拆解和难度，不在那些以 `.sharedAssets` 结尾的配置包里。类型树里找不到这些类。于是在 bundle 的字节里搜有没有新的明文字。

先搜到四个字母 `HVPK`。这是另一份目录的开头。目录头写了自己有多长、有多少条。每一条是一个名字、在文件里从哪开始、有多长。每条内容以 `HVAF` 开头，这四个字母后面才是数据。

数据一开始的两个字节是 MessagePack 的标记，表示后面是一串原始字节。把这层去掉，再用每个字节的低 7 位拼出一个长度。这个字节的最高位如果是 1，表示长度还没完，要继续读下一个字节。长度后面是资源的名字，然后是一组 32 位整数。

这些记录之间用物品的数字编号互相指向。任务要的东西、拆开能得到的东西、掉落行里的东西，都是这个编号。一条记录上如果还有「某个标记满足了才算」或者「同一次结算里的第几轮才计算」，那就是这条记录自己的字段。看到页面上一个百分数，不能再另外乘一个倍率。界面上的一句说明，和配置里真正生效的开关，也可能是两个字段。以读到的开关为准。

版本号也有好几条挨在一起。`globalgamemanagers` 里，visionOS 和 tvOS 的版本字符串是 `1.0`。后面一条字段名叫 `bundleVersion`，游戏运行时读到的版本是它。Steam 安装信息里的 `buildid` 是这一次下载的构建号。exe 属性里的 ProductVersion 是 Unity 引擎的版本，这款是 `6000.3.18f1`。这几个数各自留着。



## Summary

客户端以后如果更新了，还是先看 `StreamingAssets/aa/catalog.bin` 指向哪些 bundle，再拿 `dump.cs` 里的字段去读。
